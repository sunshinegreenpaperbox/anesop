# 第 7 章 待讨论与待决策清单


## 7.1 决策机制

施工前方案评审的目的不是"把文档看完"，而是把会挡住施工的问题当场定掉。本章把尚未闭环的问题集中成 22 项决策，按"是否阻断开工"分三级：

| 级别 | 含义 | 处理要求 |
|---|---|---|
| P0 阻断 | 不决策就无法开工或会导致返工 | 2026-11-27 方案冻结会前必须闭环，至少定"方向 + 责任人 + 截止日" |
| P1 影响设计 | 影响架构、接口或交付方式，可在 Sprint 0 内闭环 | 2026-12-18（M1）前闭环 |
| P2 影响上线 | 影响验收、预算或二期，不阻断编码 | 2027-02-26 前闭环 |

表 7-1 决策分级与处理要求

决策运转规则：

1. 一事一议，当场记录。每个决策项在 GitHub 建一条 decision 类型 Issue，标题格式 [D-xx] 主题，正文使用决策模板（背景、选项、建议、影响、结论）。结论一经确认，同步落到 ADR（docs/adr/NNNN-*.md）并回写本章。

1. 单一拍板人。每条决策指定一名拍板人（客户方或项目组），避免"集体负责等于没人负责"；其他人可以反对，但需在会前书面提出。

1. 超期默认走建议方案。到期未决且无书面异议的，按"建议方案"执行，并在下次例会追认；涉及合同、合规、临床安全的除外（必须显式决策）。

1. 决策可逆性优先。同等条件下优先选可逆方案（如先单体后拆分、先 PG 后国产库适配），把不可逆决策（合同边界、数据迁移、认证方案）尽量往后放，但不得晚于表中期限。

1. 决策变更留痕。已闭环决策若需推翻，必须新建 Issue 说明触发原因、影响范围与回滚成本，禁止在群里口头改口径。

## 7.3 阻断类决策（P0）


### D-01 试点医院与建设边界

背景：方案中的 30 间手术间、3.5 万例/年、单院交付均为假设 A-01/A-02。若实际为多院区或含日间手术中心，排程与权限模型要改，工作量增加约 15%–25%。

选项：

| 选项 | 内容 | 优点 | 代价 |
|---|---|---|---|
| A | 单院区 30 间，一期不含日间手术 | 范围清晰、可 31 周交付 | 二期需扩展 |
| B | 单院区 + 日间手术中心 | 覆盖更全 | 排程与随访模型复杂化，+4–6 周 |
| C | 多院区集团化 | 一次到位 | 权限、数据隔离、部署复杂度大幅上升，不建议一期做 |

表 7-3 试点范围选项对比

建议：A。一期把"单院区跑通、可复制"作为目标，日间手术与分院区放二期。

不决策的后果：排程、权限、部署三块设计无法冻结，S1 无法开工。

拍板人/期限：客户项目负责人 / 2026-11-20。


### D-02 后端技术栈

背景：后端选型决定招人、交付、运维与 AI 生成代码的稳定性。候选：Java（Spring Boot）、Node.js（NestJS）、.NET。

选项对比：

| 维度 | Java 21 + Spring Boot 3.4 | NestJS + TypeScript | .NET 8 |
|---|---|---|---|
| 医院私有化交付与运维接管 | 强，生态与人才最成熟 | 中，院内运维熟悉度低 | 中，Windows 环境友好 |
| 中间件与国产化适配 | 强（达梦/金仓/东方通均有适配） | 弱 | 中 |
| AI 生成代码稳定性 | 强（模式标准化、示例多） | 强 | 中 |
| 前后端同语言收益 | 无 | 有（类型共享） | 无 |
| 团队招聘难度 | 低 | 中 | 中 |

表 7-4 后端技术栈选项对比

建议：Java 21 + Spring Boot 3.4 + MyBatis-Plus。理由：医疗行业存量系统、第三方接口、等保整改与运维接管都更顺；AI 对 Spring 模式生成质量稳定；国产化路径清晰。

不决策的后果：M1 工程骨架无法搭建，Sprint 0 空转。

拍板人/期限：架构师 + 技术负责人 / 2026-11-20。


### D-03 架构形态与拆分时机

背景：8 大模块 + 公共支撑，交付人力 9.5 FTE（编制 11 人）。微服务能解耦但会带来分布式事务、联调、运维成本；单体开发快但边界容易腐化。

建议：模块化单体（Maven 多模块 + 前端按模块分包），模块间只走应用服务接口与领域事件，禁止跨模块访问数据表。M5 联调完成后，按"采集网关、报表/驾驶舱、集成平台"三个天然边界评估是否拆分，其余模块保持单体。

判定信号（满足两条以上再拆）：单模块独立发布频率显著高于整体；某模块资源消耗成为瓶颈；团队规模超过 15 人且按域分组。

拍板人/期限：架构师 / 2026-11-27。


### D-04 数据库与信创要求

背景：客户是否强制信创（国产 CPU/OS/数据库/中间件）直接决定选型、测试矩阵与工期。PostgreSQL 16 功能与运维最均衡；达梦 DM8、人大金仓 KingbaseES 需额外适配与认证。

选项：

| 选项 | 说明 | 影响 |
|---|---|---|
| A | PostgreSQL 16，不强制信创 | 工期与成本最优，SQL 尽量标准写法 |
| B | PostgreSQL 开发 + 国产库适配层 | 兼顾，需增加 4–6 周兼容测试 |
| C | 直接国产库 | 合规最强，但生态工具与团队经验风险高 |

表 7-5 数据库与信创选项对比

建议：一期 A，若合同明确信创则 B；无论哪种，SQL 禁止使用数据库特有语法，MyBatis-Plus 分页与 JSON 处理统一封装。

拍板人/期限：客户信息科 + 架构师 / 2026-11-20。


### D-05 电子签名与无纸化范围

背景：麻醉记录单属于病历，签名涉及《电子签名法》与院方无纸化进度。CA 厂商、签名范围（记录单/知情同意/麻醉总结）、是否保留纸质，直接影响归档与流程设计。

建议：一期"记录单 + 麻醉总结"CA 签名，知情同意按院方现状（可纸签扫描上传）；上线后纸电并行 2 周，验收前完成签名有效性验证与时间戳核对。

拍板人/期限：医务处 + 麻醉科 / 2026-11-27。


### D-06 设备采集范围与责任

背景：设备数据自动采集是本系统价值核心，但协议、端口、厂商配合度不确定性最高。需要明确采哪些设备、谁买采集盒、谁开放协议、谁负责现场布线。

建议范围：麻醉机、监护仪、输注泵、BIS、肌松监测、血气分析（6 类）；采集盒与串口服务器由项目采购，设备科协调厂商开放协议与端口；老旧设备先手工补录，二期改造。

风险提示：至少预留 3 周现场调试窗口，并在 M1 阶段完成 1 台设备的端到端验证（POC），避免 M3 才发现协议不通。

拍板人/期限：麻醉科 + 设备科 / 2026-11-27。


## 7.4 架构与技术类决策（P1）


### D-07 前端框架与组件库

建议：Vue 3.5 + TypeScript + Vite + Element Plus + Pinia + ECharts。理由：表单密集的医疗后台开发效率高、国内组件生态成熟、AI 生成示例充足。若团队 React 经验显著更强则改用 React + Ant Design，但需在 2026-12-04 前定，避免双栈。

拍板人/期限：前端负责人 / 2026-12-04。


### D-08 HIS/EMR 集成方式与责任边界

待确认：接口由第三方厂商提供还是院方信息科统建平台提供；是否支持 HL7 v2；患者主索引以谁为准；联调窗口如何排。

建议：院方牵头签三方接口备忘录；优先 HL7 v2（HIS 常用），EMR 文书走 REST/视图；本项目提供接口适配层与桩服务，第三方按约定时间开放测试环境；接口变更走版本管理，禁止口头改字段。

拍板人/期限：信息科 + 第三方厂商 / 2026-12-11。


### D-09 等保与电子病历评级目标

建议：等保三级（系统上线前完成备案与测评整改），电子病历系统应用水平分级评价目标 5 级（评级周期长，本项目负责数据与功能支撑，测评由院方组织）；测评整改责任与费用在合同中写明。

拍板人/期限：信息科 + 医务处 / 2026-12-11。


### D-10 排程规则与算法

待确认：排程由谁主导（麻醉科还是手术室）；急诊加台审批链；是否要求自动优化（如按术间利用率自动排）。

建议：一期做"规则可配置 + 冲突检测 + 人工拖拽"，规则项（术间、台次、时长、优先级、资质、隔离、设备）参数化；自动优化算法列为二期，避免一期陷入算法调参。

拍板人/期限：麻醉科主任 / 2026-12-04。


### D-11 麻精药品管理边界

建议：一期覆盖术间使用登记、基数管理、空安瓿回收、日结/班结、双人核对与台账报表；处方开具与药房发药主流程仍由药房系统承担，双方通过接口对账。若院方要求全流程闭环，需增加药房侧改造，工期 +3–4 周。

拍板人/期限：药剂科 + 麻醉科 / 2026-12-18。


### D-12 耗材 UDI/SPD 对接与硬件

建议：高值耗材一物一码（UDI），术间扫码登记，患者绑定与计费核对；扫码枪按术间配置，PDA 用于库房盘点；SPD 走接口，若院方无 SPD 则系统内置轻量库存。

拍板人/期限：设备科/库房 / 2026-12-18。


### D-13 质控指标口径与上报

建议：以国家麻醉质控中心指标为基线，院级指标通过规则配置扩展；每个指标定义分子、分母、排除项、数据来源与责任人；上报格式按平台模板导出，接口化留二期。

拍板人/期限：质控负责人 / 2026-12-18。


### D-14 驾驶舱指标与数据时效

建议：术中态势与告警准实时（≤30 秒），运营与质控指标 T+1；大屏分辨率 1920×1080 起，4K 适配；指标口径与第 2 章报表清单一致，避免"大屏一套、报表一套"。

拍板人/期限：医务处 + 院办 / 2027-01-15。


### D-15 AI 工具与数据合规

红线：患者数据（含姓名、住院号、身份证、影像、文本记录）不得进入任何外部大模型；生产环境不调用外部模型。

建议：研发期使用企业版或私有化部署模型；代码与提示词中只允许合成/脱敏数据；供应商合同写明"数据不用于训练"；生成代码的知识产权与许可证做审查；AI 使用情况在 PR 中声明并留痕。

拍板人/期限：信息科 + 法务 / 2026-11-27。


### D-16 团队编制与驻场

建议：按事实卡 §9 的 9.5 FTE 交付人力（编制 11 人，含临床顾问 3 人兼职，每周不少于 4 小时）；试点期（2027-06-07 起 4 周）实施、测试、前端各 1 人驻场；客户侧配 1 名项目对接人与 1 名信息科接口人。

拍板人/期限：项目经理 + 客户 / 2026-12-04。


## 7.5 交付与商务类决策（P1/P2）


### D-17 上线策略与数据迁移

建议：先选 1 个麻醉组、4–6 间手术间试点 4 周，稳定后按周分批推广至全院；历史数据只迁"患者基本信息 + 历史手术例数汇总"，不迁历史波形与原始记录（成本高、价值低）；如需迁近 3 年记录单 PDF，单列工作量。

拍板人/期限：医务处 + 麻醉科 / 2027-01-15。


### D-18 验收标准与付款节点

建议：四段验收——功能验收（模块清单逐项）、性能验收（事实卡 §5 指标压测）、安全验收（等保测评/渗透测试报告）、试运行验收（4 周可用率 ≥99.5%、记录完整率 ≥98%、接口成功率 ≥99%、用户满意度 ≥85%）；付款与四段验收挂钩，具体比例按合同。

拍板人/期限：客户项目负责人 / 2027-02-26。


### D-19 知识产权与开源合规

建议：定制开发部分客户享有使用权，通用产品与框架归承建方；开源组件建立白名单（许可证类型、版本、用途），禁止引入 AGPL/未知许可证；交付时提供 SBOM（软件物料清单）。

拍板人/期限：法务 + 项目经理 / 2027-02-26。


### D-20 预算与采购清单

待确认：采集盒数量与单价、CA 证书与签名服务、大屏与工控机、扫码枪/PDA、服务器与存储、等保测评费、第三方接口改造费。

建议：软硬件与第三方费用单列，不打包进开发报价；采集盒按术间数 +20% 备件；预算在 2026-12-31 前锁定，避免中途追加。

拍板人/期限：客户 + 商务 / 2026-12-31。


### D-21 报表口径与绩效方案

建议：系统负责"出数"（口径可配置、可追溯），绩效分配规则由院方绩效办另定；工作量报表需明确麻醉时长起止点、台次计数规则、加班判定，避免上线后口径争议。

拍板人/期限：麻醉科 + 绩效办 / 2027-02-26。


### D-22 二期范围与产品化

建议：二期候选：科研数据平台、AI 风险预警、日间手术、多院区集团化、移动端患者服务；产品化前提是一期形成可配置能力（规则、报表、流程、界面），并在合同中约定复制推广的授权方式。

拍板人/期限：双方管理层 / 2027-03-31。

## 7.7 方案评审会议建议议程

建议安排 2 小时评审会，先决 P0、再议 P1，P2 留书面征询：
