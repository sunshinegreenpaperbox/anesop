# 第 4 章 工程管理与协作机制

本章规定 31 周建设期（2026-11-30 至 2027-07-02）的工程管理办法：以 GitHub 为单一事实源，需求、任务、代码、评审、测试、发布、文档全部落在可审计位置。


## 4.1 管理原则

六条原则均对应可检查机制。

• 单一事实源：需求在 Issue、进度在 Projects、代码在仓库、决策在 ADR、发布在 Release。无对应 Issue 或 ADR 的结论视为未生效。

• 透明可视：客户方项目组持只读账号访问 Issues 与 Projects，进度、缺陷、风险不靠周报转述。

• 小步可回滚：单 PR ≤400 行、分支存活 ≤3 天、发布带回滚脚本，任何变更 2 小时内退回上一版本。

• 质量门禁前置：覆盖率、静态检查、契约、漏洞阈值写进流水线，不通过无法合并，不依赖评审人记性。

• AI 产出与人对等审查：AI 代码走同一 PR 通道、同一门禁，人类评审署名；临床安全逻辑另加临床复核（第 5 章）。

• 临床安全优先：进度与"记录不丢、不改、不错"冲突时无条件让位，延期走变更单显性记录，不在功能里悄悄降级。

见表 4-1。

| 原则 | 落地机制 | 检查点 |
|---|---|---|
| 单一事实源 | Issue/Projects/ADR/Release 四入口固定 | 每个决策可反查 Issue 号 |
| 透明可视 | 客户只读账号 + 双周演示 | 每周五更新对外视图 |
| 小步可回滚 | PR ≤400 行、分支 ≤3 天、带回滚脚本 | 每日检查滞留 PR |
| 门禁前置 | Actions 必需状态检查 | 未通过禁止合并 |

## 4.2 仓库与目录结构


### 4.2.1 monorepo 理由

单仓库承载前后端与契约，三条理由成立：

1. 契约同源：packages/contracts 的 OpenAPI 3.1、TS 类型与 Java DTO 与实现同提交变更，一次 PR 完成四处同步，杜绝"接口改了另一仓没跟上"。

1. 规模匹配：9.5 FTE 交付人力、单一交付目标，多仓的权限、流水线、版本对齐成本高于收益；分域评审用 CODEOWNERS 比拆仓更轻。

1. 门禁统一：一套 Actions 覆盖全部模块，阈值只维护一份。

代价是体积与 CI 时长，对策为路径过滤、模块级增量构建与缓存，大文件走 Git LFS。

## 4.3 Issue 体系与任务卡

Issue 是最小任务单元。包括"写一份文档""确认一个字段"在内，所有工作必须有 Issue；无 Issue 的工作不进统计与发布说明，进度由状态汇出。

Issue 表单（Issue Forms）以 YAML 定义在 .github/ISSUE_TEMPLATE/，提交时强制填写必填字段，杜绝"一句话需求"。见表 4-3。

### 4.3.3 DoR 与 DoD

就绪定义（Definition of Ready，DoR）是进入 Sprint 的闸门，完成定义（Definition of Done，DoD）是关闭 Issue 的闸门，检查人分别为产品经理与测试工程师。

DoR：

• [ ] 临床场景与角色明确，已写明涉及 R1–R12 中哪些角色

• [ ] 验收标准可判定（有数值或明确是/否条件）

• [ ] 影响模块（M0–M8）与涉及目录已标注

• [ ] 接口契约草案或字段清单已附，外部依赖注明 I-01…I-14

• [ ] 测试要点覆盖正常、边界、异常各一条

• [ ] 依赖已链接，无未决依赖

• [ ] 已估算且 size ≤L，超过则拆分

DoD：

• [ ] 已合入 main，CI 全绿，覆盖率达标（4.7.2）

• [ ] 单测与契约测试覆盖新增逻辑，核心域有正向与反向用例

• [ ] 权限、审计、脱敏三类横切检查已确认

• [ ] 文档已同 PR 更新（4.8.3 判定）

• [ ] 已部署 dev 并人工验证，附截图或录屏

• [ ] 变更日志条目已写，提交符合 Conventional Commits

• [ ] AI 参与部分已人工复核并在 PR 署名

• [ ] 无 P0/P1 缺陷，needs-clinical-review 已确认


### 4.3.4 与第 5 章任务卡的衔接

Issue 即任务卡：AI 任务卡承载输入上下文、约束与验收用例，执行后以 PR 回写并关联 Issue，Issue 内用任务列表勾选。任务卡脱离 Issue 单独存放，评审人无法判断 AI 改了哪些文件、是否碰了禁止目录。

三条规则：字段与第 5 章任务卡同名；每张卡有一名人类负责人；PR 必须含"AI 参与声明"（工具、版本、范围、复核人），缺失可直接拒绝。

## 4.5 分支模型与提交规范


### 4.5.1 trunk-based 与 GitHub Flow

采用 trunk-based 开发，形式与 GitHub Flow 一致：main 始终可发布，改动从 main 切短分支，经 PR 与门禁回到 main。不设常驻 develop：9.5 FTE 团队护不住双干合并成本，develop 易退化为长期偏离的临时主干。GitFlow 仅作备选记录——若客户要求严格版本列车并同时维护多个生产版本，可临时引入 develop，须在 ADR 中说明。

硬约束：短分支存活 ≤3 个工作日，CI 每日 09:00 查超期分支并在 Issue 提醒，第 4 天由架构师定夺。发布分支切出即冻结，只收 main 验证过的缺陷 cherry-pick。分支类型见表 4-9。

| 分支 | 命名 | 来源 | 生命周期 | 合并 |
|---|---|---|---|---|
| 功能 | feat/<issue>-<slug>，如 feat/1234-schedule-conflict | main | ≤3 天 | squash |
| 缺陷 | fix/<issue>-<slug> | main | ≤2 天 | squash |
| 杂务 | chore/<issue>-<slug> | main | ≤2 天 | squash |
| 发布 | release/<x.y> | main | ≤5 天 | cherry-pick，回合并 |
| 热修 | hotfix/<x.y.z> | v<x.y.z> 标签 | ≤1 天 | 回合并 main 与 release/x.y |

### 4.5.2 Conventional Commits 与 AI trailer

提交遵循 Conventional Commits 1.0.0，commitlint 在钩子与 CI 双重校验。格式 <type>(<scope>): <subject>，正文写"为什么改"。scope 收敛为 m0…m8、web、api、contracts、gateway、db、deploy、docs。类型见表 4-10。

| type | 含义 | 版本影响 | 示例 |
|---|---|---|---|
| feat | 新功能 | minor | feat(m2): 支持记录单锁单后修订 |
| fix | 缺陷修复 | patch | fix(gateway): 断网补传去重 |
| perf | 性能优化 | patch | perf(api): 排程查询加复合索引 |
| refactor | 重构不改行为 | 无 | refactor(m1): 抽离排程规则引擎 |
| test | 测试补充 | 无 | test(m2): 补签名验签失败用例 |
| docs | 文档 | 无 | docs(adr): ADR-0012 波形存储选型 |
| build/ci | 构建与流水线 | 无 | ci: 增加镜像扫描阶段 |
| chore | 杂务 | 无 | chore(deps): 升级 Spring Boot 3.4.2 |
| revert | 回滚 | 视情况 | revert: feat(m2): xxx |

### 4.6.2 规模与评审时限

单 PR 有效改动（排除 lockfile、生成物、格式化噪音）≤400 行，由 CI 用 git diff --numstat 扣除白名单后计算并评论到 PR；超 400 行须说明理由并经架构师 24h 确认，超 800 行必须拆分。

评审 SLA：首轮 24h 内出结论，核心域（M2、M0 权限审计、契约变更）12h。超时升级：第 25h 频道提醒，第 48h 由架构师或项目经理换人。结论只有批准、请求修改、拒绝。

### 4.7.3 制品与版本

制品包括：前端静态包、后端 JAR、网关发行包、四个镜像、SBOM（CycloneDX）、依赖与许可证清单。版本遵循语义化 2.0.0：major 在不兼容接口或验收基线变更时递增，minor 对应迭代新增，patch 为修复。

镜像打 <semver> 与 <git-sha> 双标签，生产按 digest 锁定，禁用 latest。发布在 Releases 固化版本号、变更日志、镜像摘要、SBOM、迁移脚本与回滚说明，保留最近 10 个版本。


### 4.7.4 发布、变更单与回滚

发布窗口固定周二、周四 20:00–22:00，避开手术高峰；试点上线另行约定【待确认】。生产发布必须有"发布变更单"Issue（模板 release.yml）：版本与镜像摘要、变更清单、影响范围、验证清单、回滚方案与执行人、通知对象；未审批不发布。

回滚三级：应用回滚用 scripts/rollback.sh <env> <version> 重部署上一版本，目标 10 分钟；配置按版本管理随应用同步回滚；数据迁移遵循 expand-contract（先加字段后改逻辑、分两次发布），保证旧版本可读新库，不可逆迁移须声明并先做备份与恢复验证。

回滚演练：M5 前完成 1 次 staging 完整回滚，M6 前完成 1 次含数据库的演练，记录入 docs/ops/rollback-drill.md；未通过演练的版本不得进生产。

表 4-17 文档体系与责任

ADR 回答"当时为什么这么选"，五段式：状态（提议/已接受/已废弃/被取代）、背景与约束、决策、备选与放弃理由、后果。文件名 ADR-<四位序号>-<kebab-slug>.md，编号连续不复用，头部写日期、决策人、关联 Issue。要写 ADR 的标准：影响两个以上模块、涉及外部依赖或部署形态、涉及安全合规、未来可能被推翻。预计 20–30 篇，覆盖 D-02、D-03、D-04 等决策项。

### 4.9.4 UAT 与回归

UAT 在 uat 环境进行，参与方为临床顾问、客户信息科与试点科室骨干，四条规则：

1. 前置：前 3 个工作日冻结环境与数据，发布 UAT 版本与按角色分册的脚本；客户问题由信息科录入 Issue。

1. 执行：按 M1–M8 分模块，每模块 1–2 天，脚本 + 自由探索；临床记录类由麻醉医师完成签名与修订全流程。

1. 闭环：缺陷当日分级，P0/P1 当日反馈修复计划；结束出《UAT 报告》，含执行率、通过率与未闭环项。

1. 准出：用例执行率 100%、P0/P1 清零、P2 有排期、临床顾问签署确认。

回归策略：PR 级跑 10 条核心冒烟；夜间全量 E2E，不稳定用例 24h 修复否则隔离建 Issue；Sprint 末全量回归；发布前全量 + 迁移回归（上一版本备份恢复到 staging）+ 回滚演练结论；每个里程碑固化回归清单与自动化快照。
