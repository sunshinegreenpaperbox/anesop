# ADR-0001 工程骨架与模块布局

- 状态：已接受
- 日期：2026-11-12
- 决策人：自动施工代理（按 AUTONOMY §2 默认决策）
- 关联：S0-02 / BASELINE §1 / AGENTS.md「模块边界与依赖禁令」/ D-03

## 背景与约束

S0-02 需要把方案书 §3.2 的模块化单体落成可编译、可测试、可扩展的工程骨架。约束：
Java 21 + Spring Boot 3.4、Vue 3.5 + Vite 6；`apps/api/modules/m0..m8` 各含 `api`/`impl`；
`scripts/check.sh` 以 `apps/api/pom.xml` 为后端入口；Docker 不可用（EXT-08）；home 只读、
依赖缓存必须落在仓库内。方案未逐行规定目录名、artifactId、聚合方式与版本补丁号，需按
"可逆、最简单、与现有代码一致"自行决定并记录。

## 决策

1. **Maven 层级**：根 `pom.xml`（`anesop-parent`，packaging=pom，继承
   `spring-boot-starter-parent:3.4.5`，`<modules>` 只含 `apps/api`）→ `apps/api/pom.xml`
   （聚合 `api-bootstrap` 与 `modules/m0..m8`）→ `apps/api/modules/mX/pom.xml`
   （聚合 `api`、`impl`）。实际 artifactId：`mX-api`、`mX-impl`，包名
   `com.anesop.mX.api` / `com.anesop.mX.impl`。这样既满足"每模块分 api/impl"，
   又与任务卡写域 `apps/api/modules/m0/` 一致；后端构建入口固定为 `apps/api/pom.xml`。
2. **启动装配**：`api-bootstrap` 是唯一 Spring Boot 可执行模块；S0-02 阶段只依赖各
   `mX-api`（模块间只依赖 api 的编译期约束），`mX-impl` 的运行时装配在 S0-07 认证
   权限骨架时补齐（届时必须有真实实现类，避免空装配）。
3. **版本锁定**：后端版本集中在根 pom `<properties>` + `<dependencyManagement>`，
   子模块不写版本；前端 `package.json` 用精确版本（禁 `^`/`~`），`pnpm-lock.yaml` 入库。
   Docker 不可用期间不引入需要容器的依赖，Testcontainers 只锁 BOM 版本。
4. **前端结构**：`apps/web` 单包（Vue 3 + TS + Vite），路由壳 + `src/modules/m0..m8`
   分包占位；组件库/图表（Element Plus/ECharts）推迟到 S0-08 按需引入，避免骨架阶段
   无谓体积。
5. **ArchUnit 真实可执行**：三条铁律（api 不依赖 impl、impl 不互依赖、模块无环）写入
   `ModuleBoundaryTest`，并用 `com.anesop.archfixture` 测试夹具做负向对照，断言规则确实
   会报错，避免"恒真断言"。S0-02 阶段真实模块无实现类，规则以 `allowEmptyShould(true)`
   过渡；S0-07 装配 impl 后移除该开关（已在测试注释与交接单中登记）。
6. **构建脚本约定**：根 `package.json` 用 `pnpm -r --if-present` 串联子包脚本，
   S0-03/11 落地 lint/单测后无需改命令；`apps/web build` = `vue-tsc --noEmit`
   + `tsc -p tsconfig.node.json --noEmit` + `vite build`。

## 备选与放弃理由

| 备选 | 放弃原因 |
|---|---|
| 根 pom 不聚合、各模块独立构建 | `mvn verify` 无法一次构建，CI 与 check.sh 复杂化 |
| 模块目录用 `m0-api/`、`m0-impl/`（而非 `m0/api/`） | 与 AGENTS/"各含 api、impl 子模块"及任务写域表述不一致 |
| 引入独立 BOM 工程/平台模块 POM | 单院模块化单体，多一层继承增加理解成本，收益为零 |
| 骨架阶段即引入 Element Plus/ECharts/Vitest | 未使用先引入违反"按需依赖"，且拖慢安装与构建 |
| springdoc 用 2.8.x BOM 替代 | 越过 Boot 3.4 对齐的 minor，风险大于收益 |

## 后果（正面/负面/代价）

- 正面：单命令构建全后端；模块边界编译期可验证；版本单点锁定；前端与后端互不阻塞。
- 负面：Spring Boot 版本由 `spring-boot-starter-parent` 提供，自定义父 POM 能力受限
  （可接受，后续如需完全自控再改 import BOM）；空模块 jar 仅含 `package-info`。
- 代价：S0-02 首次构建需下载依赖（约 5.5 min），之后增量 verify 约 23 s；`impl`
  运行时装配必须在 S0-07 补齐，否则应用启动看不到实现（已在交接单登记）。
- 已记录的实现细节偏差：`springdoc-openapi-bom:2.7.0` 未在 Maven Central 发布，改为
  根 pom 显式 `dependencyManagement` 锁 starter 2.7.0；Testcontainers 按 1.20.4 覆盖
  Boot 默认值；`pnpm-workspace.yaml` 同时写 `allowBuilds`（pnpm 11）与
  `onlyBuiltDependencies`（pnpm 10），S0-04 固定 pnpm 版本时统一。
