# ADR-0012 停改台/急诊审批：未发布窗口的契约收紧与双人双控前置

- 状态：已接受（待人工终审）
- 日期：2026-11-13
- 决策人：自动施工代理（按 AUTONOMY §2 默认决策；M2-M2-02 独立评审 Q-1/Q-2/Q-3 触发）
- 关联：ADR-0011、M2-M2-02、`packages/contracts/openapi/scheduling.yaml` 0.5.0、
  `docs/modules/m1/README.md` §4.3、`db/migration/V9__m1_schedule_change_emergency.sql`

## 背景

M2-M2-02 独立评审提出三项处理意见：

- **Q-1**：改台 `PUT /v1/scheduling/schedules/{scheduleId}` 的 `reasonCode` 在 0.5.0 内改为
  必填，与方案书 §2.4.2「停台改台必选原因码」对齐。
- **Q-3**：急诊加台端点从未返回 200（控制器固定 201），移除契约中不可达的 200 成功响应。
- **Q-2**：MVP 由执行人自批（`requested_by = approved_by`）存在自我审批风险。

Q-1 与 Q-3 相对 HEAD 中已提交的 scheduling 0.4.0 baseline 均属 oasdiff 破坏性变更
（`new-required-request-property`、`response-success-status-removed`），而 0.5.0 尚未发布、
无生产消费者。

## 决策

1. **未发布窗口内的显式收紧**：接受 Q-1/Q-3 在 0.5.0 内完成，不升 major。理由是 0.5.0 未
   发布、无外部消费者，且 M2 契约尚未冻结（`docs/api/README.md` §7）。合入前必须：
   - 由独立评审确认两项收紧；
   - 将评审通过的 0.5.0 契约复制到 `baseline/scheduling.yaml` 并**随同一 PR 提交**；
   - 提交前 `scripts/contract-check.sh` 的 HEAD baseline 步骤会红（这是预期的防自证机制），
     提交 0.5.0 baseline 后自动转绿；禁止为过检关闭或绕过该步骤。
2. **完全 append-only**：`schedule_change_request` 的审批结果在同一事务内以 APPROVED 行写入，
   V9 触发器拒绝 UPDATE/DELETE/TRUNCATE（SQLSTATE 55000）；不实现 PENDING→APPROVED 的状态回写。
3. **双人双控前置（Q-2）**：当前单人审批仅用于 MVP 合成数据与开发验收。正式上线前必须由 M6
   提供独立审批角色/双人双控（或等效的医务处审批流），并在发布检查单中作为准入项；在此之前
   不得接入真实患者数据。该项登记于 `docs/modules/m1/README.md` §4.3 与本 ADR。

## 备选与放弃理由

| 备选 | 放弃原因 |
|---|---|
| 保持 `reasonCode` 可选、仅服务层必填 | 契约与实现不一致，前端可静默不选，违背方案书 §2.4.2 |
| 保留急诊 200 死响应 | 契约声明了永不返回的状态码，误导调用方与契约测试 |
| 升 1.0.0 立即清理 deprecated 端点 | 1.0.0 清理需独立 major 发布与消费方迁移，超出 M2-M2-02 范围 |
| 为过 HEAD 门禁改写 `contract-check.sh` | 会削弱 ADR-0011 的防自证机制；应通过提交评审后的 baseline 转绿 |

## 后果

- 正面：契约与实现/蓝图一致；审批留痕不可篡改；自我审批风险有明确上线前置。
- 负面：0.5.0 合入前 HEAD baseline 门禁红，需要评审人确认后提交 baseline；单人审批在 M6
  完成前不能用于生产。
- 解除条件：M6 双人审批上线并在发布检查单签字；0.5.0 baseline 提交后 HEAD 门禁恢复绿。
