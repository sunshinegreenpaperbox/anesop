## 背景与约束

FINAL-REPORT §6.2 遗留「M0 字典 API/消息中心/文件管理」是最优先补齐的基础能力缺口：
V1 已建 `sys_dict_type/sys_dict_item` 与 RBAC/审计骨架，但缺 API、缺消息与文件的落库结构。
补全时必须同时满足四条硬约束：

1. **不得存 PHI**（AGENTS 红线）：字典、消息参数、文件内容都不能成为患者数据的旁路；
2. **不引入新依赖**（AGENTS 依赖准入）：文件上传不做 multipart 流式（需要新解析器/网关配置），
   消息不做 WebSocket/邮件/短信（通道为 EXT）；
3. **Docker/MinIO 不可用**（EXT-06/EXT-08）：文件存储必须可本地运行、可替换；
4. **权限与审计属核心域**：字典维护仅管理员、消息仅本人、文件按业务可见性，并且全部留痕。

## 决策

### 1. 字典：全院参考数据，读全院、写仅管理员，编码不可变、停用不删除

- 语义：字典是**参考数据**（性别、ASA、手术紧急度、术间/病例状态、角色类型），不是业务数据，
  不按数据范围裁剪；`GET /v1/dicts`、`GET /v1/dicts/{type}` 只需 `m0:dict:read`。
- 写入：`POST/PUT/DELETE /v1/dicts/{type}/items` 需 `m0:dict:write`，V27 **仅授予 `SYS_ADMIN`**；
  服务层再校验 `SYS_ADMIN` 角色（纵深防御，防止后续误授权）。
- 唯一性：沿用 V1 `uk_sys_dict_item_type_code (dict_type_id, code)`，即「同类型内项编码唯一」；
  V27 不重复建约束，只补读路径排序索引 `(dict_type_id, sort, code)`。
- **编码不可变**：`code` 是历史记录解释字典语义的稳定标识，更新请求体不含 `code`；要改语义
  应新增编码并停用旧编码。
- **逻辑停用**：`DELETE` 只置 `status=0`（接口 `enabled=false`），不物理删除；维护端用
  `includeDisabled=true` 查看停用项，该参数**仅对持 `m0:dict:write` 者生效**，其他调用方 403。
- 字典项 `remark` 只放口径说明，禁止患者标识与临床自由文本。

### 2. 消息：只有「收件人本人可见」，写入只走内部发布器，不暴露任意发送端点

- `sys_message` 以 `recipient_user_id` 为隔离边界；查询/已读一律附加
  `recipient_user_id = 当前用户`，**非本人与不存在统一 404**（不泄露他人消息是否存在）。
- **不提供** `POST /v1/messages` 之类的任意发送接口：消息只能由领域事件/系统广播经
  `MessagePublisher` 写入（`m0-api` 接口，`m0-impl` 实现）；需要新消息类型的模块在自己的
  领域事件里调用发布器，避免 M0 变成“任意通知通道”。
- **模板注册表（S-4）**：`MessageTemplates` 登记 `code → 类型/固定标题/允许参数键`（当前
  `SYSTEM_BROADCAST`、`SCHEDULE_CHANGED`、`SCHEDULE_STOPPED`、`ALERT_CRITICAL`、
  `QC_REVIEW_DUE`、`TASK_ASSIGNED`、`MATERIAL_LOW_STOCK`）；`MessagePublisher` **不接收 title**，
  标题只由服务端注册表渲染，未登记编码/类型不匹配/参数越界一律拒绝，杜绝任意文案与 PHI
  进入标题。参数值 ≤200 字符且不含控制字符；PHI 合规责任仍在调用方与代码评审。
- 已读：`read_at` 幂等更新，不物理删除消息；未读角标 `unreadCount` 恒为全部未读数
  （不受 `unreadOnly`/分页影响）。
- 审计：`MESSAGE_READ`（单条，detail 只含类型与模板编码）、`MESSAGE_READ_ALL`（只含条数）。

### 3. 文件：非 PHI、类型/大小白名单、内容寻址、按业务可见性下载

- **PHI 禁令（硬）**：只允许模板/报表/附件：`application/pdf`、`text/csv`、`text/plain`、
  `image/png`、`image/jpeg`；单文件 ≤**20 MiB**。禁止临床影像（DICOM/术中照片/视频）、
  身份证明（身份证/护照/驾驶证扫描）、含患者姓名/住院号/证件号/手机号的表格与截图。
  上传方为 PHI 合规第一责任人，违规按安全事件流程处置。
- 传输：契约采用 **JSON + Base64**（`contentBase64`），不引入 multipart 新依赖；
  >20 MiB 与流式上传留待 MinIO 适配器（EXT-06），届时先升契约版本再实现。
- **文件名不持久化（B-2）**：客户端 `fileName` 只在请求内存中做语法校验（长度/路径分隔符/
  控制字符），**不写 `sys_file`、不写审计**；展示名由服务端生成
  `file-<fileId>.<ext>`（扩展名按内容类型映射）。`businessId` 只接受 UUID 或大写业务号，
  拒绝自由文本/中文/空格，避免患者标识进入业务关联列。
- 校验顺序：Base64/文件名/businessId（400）→ 类型白名单、大小、声明大小与解码长度一致（422）；
  库层 `ck_sys_file_content_type`/`ck_sys_file_size` 再兜底（纵深防御）。
- 存储：**内容寻址**，`storage_key = <sha 前2位>/<sha 3-4位>/<sha>.bin`；同一 SHA-256 只落盘一份，
  元数据每次上传独立（便于按上传者控制可见性）。文件内容不入库、不入日志。
- 部署（S-1）：compose 的 `api` 注入 `ANESOP_M0_FILE_ROOT_DIR=/var/lib/anesop/files` 并挂载
  持久卷 `m0filedata`，容器重建不丢附件；`scripts/compose-check.sh` 静态断言该变量与卷。
- 适配器：`FileStorage` 接口 + 本地 FS 实现（默认 `.cache/files`，已 gitignore；生产挂载盘）；
  **MinIO 适配器仅接口占位（EXT-06）**，接入时用 `@ConditionalOnProperty` 切换实现，不改业务代码。
- 病毒扫描：`scan_status` 当前固定 `NOT_SCANNED`（占位，**EXT-07**）；接入前不得上传外部来源文件；
  状态为 `INFECTED` 时拒绝下载（403）。
- **可见性（功能权限 + 业务对象数据范围，B-1）**（在 `m0:file:read` 之上再收紧）：
  | 业务类型 | 功能权限 | 业务对象数据范围 |
  |---|---|---|
  | `TEMPLATE` | 持 `m0:file:read` | 不适用（模板公开） |
  | `REPORT` | 持 `m4:report:read` | **当前 fail-closed**（无报表对象标识，仅上传者/`SYS_ADMIN`；Q-24） |
  | `SCHEDULE` | 持 `m1:schedule:read` | m1 `SchedulingService.get` 的 DataScope（DEPT/SELF/ROOM/SITE） |
  | `RECORD` | 持 `m2:record:read` | m2 `AnesthesiaRecordService.get` 的 DataScope |
  | `ATTACHMENT` | 仅上传者与 `SYS_ADMIN` | 不适用 |
  缺模块只读权限 → **403**；业务对象不存在/超出数据范围、文件不存在/已删除 → **404**
  （不区分“不存在”与“不可见”，防存在性泄露）；响应不含 `storageKey`（防绕过鉴权直接读盘）。
  端口 `FileBusinessVisibilityPort` 定义在 m0-api，由 api-bootstrap 适配 m1/m2，m0 不直接依赖
  业务模块；适配器异常一律 fail-closed。
- 下载响应：`Content-Disposition: attachment; filename*=UTF-8''…`（文件名过滤 CR/LF/引号/路径
  分隔符，防头注入）、`X-Content-Sha256` 完整性头、`X-Content-Type-Options: nosniff`。
- 审计：`FILE_UPLOAD` / `FILE_DOWNLOAD`，detail **只含**业务类型、大小、摘要前 12 位；
  **不含 fileName、businessId、文件内容与患者标识**（B-2）。

### 4. 权限最小授予（V27）

| 权限点 | 授予角色 | 说明 |
|---|---|---|
| `m0:dict:read` | 全部 6 个平台基线角色 | 字典全院读 |
| `m0:dict:write` | **仅 `SYS_ADMIN`** | 字典维护属平台管理员 |
| `m0:message:read` | 全部 6 个平台基线角色 | 只有本人消息可见 |
| `m0:file:read` | 全部 6 个平台基线角色 | 可见性另按业务类型收紧 |
| `m0:file:write` | 全部 6 个平台基线角色 | 临床角色需上传模板/报表/附件 |

V2 遗留的两段式 `dict:read`/`dict:write` **保留不动**（不改历史脚本）；新端点一律用三段式。
遗留权限点随 ADR-0011 在 1.0.0 大版本清理。

### 5. 前端复用入口

`apps/web/src/modules/m0/components/FileUploadPanel.vue` 以 `business-type`/`business-id` 复用：
排程页传 `SCHEDULE` + 台次标识、记录页传 `RECORD` + 记录标识；`FileCenterView` 作为一页示例。
字典管理页仅 `SYS_ADMIN` 菜单可见（`m0:dict:write`），消息中心/文件管理按读权限可见。

## 后果

- 正向：M0 基础能力闭环；字典/消息/文件的权限、数据范围、审计、PHI 禁令均可测试（见
  `PlatformDictServiceTest`、`PlatformMessageServiceTest`、`PlatformFileServiceTest`、
  `PlatformStorageTest`、`FileBusinessVisibilityAdapterTest`、`M0PlatformApiIntegrationTest`）；
  文件存储可本地运行、可平滑切换到 MinIO。
- 代价/边界：Base64 上传比 multipart 多约 33% 传输量（≤20 MiB 可接受）；病毒扫描未接入
  （EXT-07）期间不能上传外部来源文件；消息无已发送/草稿等邮件语义；字典无类型 CRUD
  （类型由迁移/实施配置维护，避免后台随意造类型）。
- 回滚：应用下线 5 个端点 + 前端菜单；库层按 V27 头部注释执行（先删授权再删权限点，最后
  DROP `sys_message`/`sys_file`/索引）；文件内容需先备份目录并登记台账。

## 备选方案与不采用原因

1. **multipart 上传**：需要新增解析器/网关 `client_max_body_size`/临时目录治理，且当前无
   MinIO，价值低于成本；留待 EXT-06。
2. **消息通用发送 API**：会成为任意通知/潜在钓鱼通道，且无法约束 PHI；改为内部发布器 +
   模板白名单。
3. **字典项物理删除**：破坏历史记录可解释性；保留逻辑停用。
4. **文件按角色硬编码可见性**：角色会随院方岗位矩阵调整；改为“业务类型 → 模块只读权限”，
   与 RBAC 权限点同源。
5. **MinIO 现在接入**：Docker/MinIO 不可用（EXT-06/EXT-08），先固定接口与本地实现，
   接入成本最低且不阻塞主线。
